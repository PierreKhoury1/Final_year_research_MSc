- `PuschRx` constructs `m_fullSlotGraph` and instantiates `m_fullSlotGraphExec` with `CUDA_GRAPH_INSTANTIATE_FLAG_DEVICE_LAUNCH` when enabled; analogous handles cover early HARQ and front-loaded DMRS. Its pre-launch graphs are host graphs and normally contain an event-record node. Setup updates executable node parameters/enabled state and uploads graphs. `run(FULL_SLOT_PROC)` still host-launches `m_fullSlotGraphExec` in the ordinary full-slot case even with device launch enabled; the flag alone does not implement periodic GPU scheduling. See [construction](https://github.com/NVIDIA/aerial-cuda-accelerated-ran/blob/4f65f97c1d5f701ce911f7dda8f1b1f3f0c7693c/cuPHY/src/cuphy_channels/pusch_rx.cpp#L1339), [launch-graph nodes](https://github.com/NVIDIA/aerial-cuda-accelerated-ran/blob/4f65f97c1d5f701ce911f7dda8f1b1f3f0c7693c/cuPHY/src/cuphy_channels/pusch_rx.cpp#L2924), [updates/uploads](https://github.com/NVIDIA/aerial-cuda-accelerated-ran/blob/4f65f97c1d5f701ce911f7dda8f1b1f3f0c7693c/cuPHY/src/cuphy_channels/pusch_rx.cpp#L7382), and [run](https://github.com/NVIDIA/aerial-cuda-accelerated-ran/blob/4f65f97c1d5f701ce911f7dda8f1b1f3f0c7693c/cuPHY/src/cuphy_channels/pusch_rx.cpp#L9832).
- NVIDIA's existing [`deviceGraphLaunchKernel`](https://github.com/NVIDIA/aerial-cuda-accelerated-ran/blob/4f65f97c1d5f701ce911f7dda8f1b1f3f0c7693c/cuPHY/src/cuphy/pusch_start_kernels.cu#L95) launches a supplied `CUgraphExec` fire-and-forget after checking the preceding symbol-wait result. Production [F08 configuration](https://github.com/NVIDIA/aerial-cuda-accelerated-ran/blob/4f65f97c1d5f701ce911f7dda8f1b1f3f0c7693c/cuPHY-CP/cuphycontroller/config/cuphycontroller_F08_CG1.yaml) enables `pusch_deviceGraphLaunchEn: 1` and work cancellation mode 2. This is an existing data-readiness mechanism, not evidence of a periodic timer executive.
- The C++ example wrapper exposes [`.handle()`](https://github.com/NVIDIA/aerial-cuda-accelerated-ran/blob/4f65f97c1d5f701ce911f7dda8f1b1f3f0c7693c/cuPHY/src/cuphy_channels/cuphy_channels.hpp#L119). Add a narrow experimental getter rather than attempting to reconstruct it through the wrapper.

## Proposed first experiment and patch files

Use one prepared full-slot test vector and one pipeline/context, with early HARQ, front-loaded DMRS, work cancellation, and green contexts excluded initially. Those are proposed scope restrictions, not verified properties of test case 7304. Assert the actual dynamic configuration before proceeding.

1. Patch `cuPHY/src/cuphy_channels/pusch_rx.hpp/.cpp` and `cuPHY/src/cuphy/cuphy_api.h` to expose a borrowed, already-configured full-slot executable handle for this restricted replay mode. Keep ownership in cuPHY; reject unsupported phase combinations. Do not clone the original source graph blindly: setup patches the executable graph, so a new instantiation must receive the same parameter and enable-state updates.
2. Patch `cuPHY/examples/pusch_rx_multi_pipe/cuphy_ex_pusch_rx_multi_pipe.cpp`, `pusch_rx_test.hpp/.cpp`, and `CMakeLists.txt`; add a CUDA executive translation unit. Add explicit launcher/period/deadline options, prepare both setup phases before measuring, synchronize uploads, and reuse identical input/state/reset semantics in CPU and GPU cases. The current [test loop](https://github.com/NVIDIA/aerial-cuda-accelerated-ran/blob/4f65f97c1d5f701ce911f7dda8f1b1f3f0c7693c/cuPHY/examples/pusch_rx_multi_pipe/pusch_rx_test.cpp#L647) inserts device synchronization, a delay kernel, and an event gate per iteration; the timed replay path must replace that loop.
3. Start with **one slot per executive tail generation** so a single cuPHY handle is never relaunched while active. Do not carry over the synthetic 100-handle pool without auditing cuPHY's internal child handles, shared state, and update lifecycle. Measure the per-slot tail overhead explicitly. A wrapper graph can stamp start and tail-launch a completion graph after the cuPHY child finishes; this measures wrapper completion latency. For exact PHY kernel execution stamps, add instrumentation inside the full-slot DAG with dependencies covering all roots/leaves.
4. Keep setup, output copies, validation, and host event bookkeeping outside the restricted replay interval. The ordinary [run phases](https://github.com/NVIDIA/aerial-cuda-accelerated-ran/blob/4f65f97c1d5f701ce911f7dda8f1b1f3f0c7693c/cuPHY/examples/pusch_rx_multi_pipe/pusch_rx_test.cpp#L238) include these operations. Capturing `run()` wholesale is not a valid shortcut: event nodes are forbidden in device-launchable graphs, and output copies need their own ordering. Repeated HARQ/CFO state and fresh-transmission reset behavior must be validated against normal execution before timing claims.

CUDA requires device-launchable graphs to be uploaded, permits only kernel/memcpy/memset/child-graph nodes, prohibits overlapping device launches of one executable, and limits each execution to 120 fire-and-forget launches. Tail launch waits for generated child work. Changes to device graphs require re-uploading. These rules constrain both the cuPHY handle and any wrapper. [NVIDIA CUDA Graphs](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html)

## Local build and interpretation

`slotbench/cloud/onstart_cuphy.sh` already builds this target and generates TC 7304; `slotbench/data/2026-10-01_a100_cuphy/README.md` records a previous A100 run. These are existing repository artifacts, not a fresh reproduction. The cloud script currently defaults `ACAR_COMMIT` to `main`; pin it to the inspected SHA and apply a checked patch before building. Its referenced `slotbench/docs/cuphy.md` is absent in this checkout.

Reuse the existing A100 build recipe for the first cuPHY validation; the RTX 3060 synthetic smoke does not establish cuPHY compatibility. Require baseline CRC/BLER/output equivalence, several tail generations without launch errors or missing records, matched CPU/GPU workload settings, raw timestamps, and explicit excluded phases. This first experiment concerns periodic replay of ready input. A production integration must additionally preserve symbol-arrival gates, changing slot descriptors, HARQ state, overlapping slot budgets, and output delivery; no production latency benefit follows from the standalone replay alone.
